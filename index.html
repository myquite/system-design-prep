How System Design Appears in Interviews (4 Formats)

From entry/mid-level discussions to senior/staff architecture rounds (00:02:10 in video)

1. Full WhiteboardingMost Common

Designing a complete system (like Spotify or WhatsApp) or a core product feature from scratch in 45–60 minutes starting from a 1-sentence prompt.

2. Bottleneck DiagnosisDebugging Scale

Inspecting an existing company architecture diagram under 10x traffic load, spotting single points of failure, and proposing targeted fixes.

3. Past Project Deep-DiveExperience

Walking through a production system you helped ship—explaining why you picked your database, how components communicated, and what you'd redesign today.

4. Conceptual Trade-OffsFundamentals

Focused probing on CAP theorem, SQL vs NoSQL isolation levels, WebSockets vs HTTP polling, CDN cache invalidation, and rate limiting placement.

The 5 Dimensions Interviewers Actually Score You On

Memorizing diagrams only covers 1 of 5 pillars. Click any dimension to toggle Senior Habits vs Common Red Flags (00:04:50 in video).

1. Communication

Treat the interviewer like a peer engineer solving a problem together—not a silent exam or a non-stop monologue.

✓ Clarify scope & check in after each phase
✗ Jumping straight into drawing boxes silently
2. Structured Thinking

Break down a vague 1-line prompt into a predictable, ordered sequence of steps so the interviewer always knows where you are.

✓ Follow the 5-step roadmap systematically
✗ Bouncing randomly between DBs, UI, and sharding
3. Technical Judgment

Justify every component choice (SQL vs Cassandra, Kafka vs Redis Pub/Sub) based on requirements—never out of habit.

✓ State pros, cons & rejected alternatives
✗ Adding Kafka or sharding for 1,000 users
4. Practical Depth

Separates engineers who have shipped real production code from pure theory learners via failure modes & observability.

✓ Discuss fallbacks, multi-AZ, alerts & retries
✗ Assuming networks and databases never fail
5. Time Management

Pace yourself across 45–60 minutes so you don't spend 40 minutes on requirements and run out of time for scaling.

✓ Propose focus areas & track phase budgets
✗ Optimizing failure modes before core design exists

Preventing Double Bookings in SQLPractical Depth
-- 1. Naive Approach (BROKEN under concurrency):
SELECT available_count FROM room_inventory WHERE room_type_id = 42 AND date = '2026-12-24';
-- Both User A & User B read available_count = 1 simultaneously!
INSERT INTO bookings ... -- Result: DOUBLE BOOKING & costly refund!

-- 2. Optimistic Concurrency Control (Atomic Conditional Update):
UPDATE room_inventory
SET available_count = available_count - 1, version = version + 1
WHERE room_type_id = 42 AND date = '2026-12-24'
  AND version = 7 AND available_count > 0;
-- Only 1 transaction affects 1 row; the second affects 0 rows and fails cleanly.

Protocol Trade-Offs: WebSockets vs HTTP Polling03:14:49
Protocol Memory & State Latency & Best Use Case
HTTP Short Polling Stateless, low server RAM per idle user High latency & wasted empty requests; suited for simple status checks.
HTTP Long Polling Holds request open until data arrives Medium latency; fallback when firewalls block WebSockets.
WebSockets (Chosen) Stateful; consumes more RAM per open connection Sub-50ms bidirectional delivery; worth the memory cost for real-time chat.

// Chat Server Feature Flag & Version Stripping Logic (03:12:57 in Course)
function deliverMessageToClient(message, recipientClient) {
  const enabledFlags = featureFlagStore.getFlagsForUser(recipientClient.userId); // e.g., 20% rollout
  const payload = { ...message };

  // Strip unsupported fields for client apps below version 2.2
  if (recipientClient.appVersion < 2.2 || !enabledFlags.includes("message_reactions_v2")) {
    delete payload.reactionsMetadata;
    delete payload.interactivePoll;
  }
  recipientClient.websocket.send(JSON.stringify(payload));
}
